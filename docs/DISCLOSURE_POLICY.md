# 公开仓披露纪律 —— 什么不能进这个仓，以及为什么

> **适用：** `trustworthy-ai-core` 是**公开仓**（GitHub `visibility: PUBLIC`）。
> **机械门：** `tools/check_doc_disclosure.py`，在 CI 里跑，命中 `error` 即 FAIL。
> **本文是那道门的说明书** —— 门告诉你"这条不行"，本文告诉你"为什么"和"改成什么"。

---

## 0. 为什么要有这道门

我们的工作天然跨私有/公开：引擎开源，运行时闭源，评测语料受限，选型涉及第三方厂商。
**靠人盯必然还会漏** —— 这已经是第 4 次同类问题（前三次：受限语料文本、内部数字↔配置
对照表、conformance fixture 产地）。前三次都被人接住了。

**第 4 次没接住：** 一段包含私有源码路径与控制缺口描述的文字**已经提交并推送到公开 main**
才被发现。发现它的是人工复核，而人工复核当时**恰好漏掉了另外两个文件**（一份 issue 文档
和一份 backlog），是这道门补扫出来的。

> **"每次都靠人接住" 不是控制，是运气 + 好记录。** 这是那个控制。

## 1. 五类不得公开的内容

| 类 | 严重度 | 为什么 |
|---|---|---|
| **control_gap** 自曝我方管控门实际没在跑 | 🔴 **最高** | 自己拆自己的台。一个把"可验证审计 / 防自证门"当护城河叙事的产品，公开宣布该门是空的，比任何外部批评都伤 |
| **vendor_named** 具名厂商 + 负面判断 | 🔴 高 | ① 触及《反不正当竞争法》§11 商业诋毁面；② 违反我方"不点名不贬损"纪律；③ 把采购谈判底牌亮给厂商本人 |
| **private_source** 私有运行时源码路径/行号 | 🔴 高 | 给出内部实现地图 |
| **platform_commit** 私有仓 commit 号 | 🔴 高 | 坐实"哪一次改动造成了什么" |
| **internal_name** 内部分层/SKU/私有文档名 | 🟠 中 | 泄露 roadmap 与包装姿态 |
| **private_repo_path** 指向私有仓的**路径** | 🔴 高 | 泄露私有仓名与目录结构；且在公开仓里是 **dangling 链接**（点开必 404）。见 §1.2 方向纪律 |
| **internal_identity** 真实部署身份（已开通用户名 / 非示例邮箱） | 🔴 高 | 泄露内部账号；更糟的是**示例会被照抄进别人的命令** —— 一个真实用户名写进 README，就等于把它发给每个读者。示例一律用占位符 `<provisioned-eval-user>` 或 RFC-2606 示例域（`*.example`） |
| *private_doc_ref* 指向私有文档的**裸交叉引用** | 🟡 **warn，不 FAIL** | 只暴露"有这么份文档"，不含其内容。dev brief 里说"契约在上游某文档"是合法且必要的 |

### 1.2 🔴 跨仓引用的**方向**纪律

**引用方向决定它是不是泄露：**

| 方向 | 判定 | 理由 |
|---|---|---|
| **私有 → 公开**（私有文档引 Core 的公开 issue 路径） | ✅ **允许** | 目标本就公开，链接可点、无泄露 |
| **公开 → 私有【路径】**（Core 文档引 `../../<私有仓>/...`） | 🔴 **禁止** | 泄露私有仓名 + 目录结构，且链接必然 dangling |
| **公开 → 私有【泛指】**（"上游标的抽象设计（私有，不公开）"） | ✅ 允许 | 说明"有这么份东西"而不暴露它在哪、叫什么 |

**改写方式**：把 `[私有文档名](../../私有仓/路径)` 换成**不带路径、不带文件名的泛指** ——
例如"上游数字对账 artifact（私有，不公开）"。**保留"存在一份上游设计"这个事实是必要且合法的**，
不必要的是它的**仓名、路径与文件名**。

### 1.1 为什么 `private_doc_ref` 只 warn

**一道会对合法交叉引用 FAIL 的门，一个月内必被关掉。** 而被关掉的门比没有门更糟 ——
大家以为它在跑。所以严重度分两级：**内容**必须拦（error），**指针**只需可见（warn）。
这条校准本身就是纪律的一部分，改门的人请先读这一节。

## 2. 中性化对照表（怎么改写）

| 私有原文 | 公开侧改写 |
|---|---|
| 具名厂商 | **候选 A / 候选 B**（不点名） |
| 私有源码路径 + 行号 | "上游侧已确认" |
| 私有仓 commit 号 | "上游规则集版本（号见私有对账）" |
| 内部分层名 / SKU 名 | "上游的规则层 / 语义层"；SKU 一律删 |
| "空门""实际没人跑""两端都空转" | "本门依赖的资产不在公开仓 ⇒ 归属见私有侧" |
| "某字段非内容派生" | "上游版本字段目前非内容派生（详见私有侧）" |
| **"未编译打包 ⇒ 泄露风险"** | **一律删** —— 这句本身就是最不该写的一句 |

## 3. 该留什么（别过度删）

**Core 必须能被独立实现。** 以下一律保留：

- harness 架构、`ProbeResult` / `VendorLabel` 契约、指标语义
- 方法学：双侧门、稳定性检查、质量/延迟分离、`corpus_sha` 冻结、fail-closed 判据
- 公开技术事实：开源软件行为、公开模型与其许可证、公开标准条款
- 实现必需的跨仓事实（"需上游提供 `content_class` 标签"）—— **去掉商业判断与内部架构名即可**
- **方法学层面的风险**（如"整条链同源会退化成自证"）——这是我们的方法论，是资产不是把柄

> 判据：**删掉的应该是"谁"和"哪里"，不是"怎么做"和"为什么"。**

## 4. 怎么用

```bash
python tools/check_doc_disclosure.py                 # 工作树（含未跟踪新文件）—— CI 跑这个
python tools/check_doc_disclosure.py --all-history    # 全历史：回答"这东西曾经发出去过吗"
```

**扫描范围包含未跟踪文件**，这是刻意的：历次事故都发生在**新文档**里，
而只读 `git ls-files` 的门会给新文件一路放行，直到 commit 那一刻 —— 那时已经太晚。

## 5. 命中之后

1. **别就地删** —— 内容通常是对的，只是**放错了仓**。先找它的私有归宿。
2. 现成的家：厂商评估 → 私有尽调文档 §7；上游实现细节 → 私有对账/设计文档。
3. 在公开侧留一行**指针 + 中性摘要**，让读者知道"这里有过判断，判断在私有侧"。
4. 若确实必须留在公开侧，按 §2 改写，**不要绕过门**（不要为了过门而把话说得含混到失真 ——
   那是另一种不诚实）。

## 6. 🔴 流量相关量的对外口径（单一可引落点 —— PROV / EV-PAIR / 未来 issue 引这里，不各自重述）

**"检测型 / 时延型"数字里有一类是「流量相关量」** —— `block_rate` / `duration_p99` / 配对 `delta` 之属：
**离开「在什么流量上测的」就没有意义。** 实证：同一个 `duration_p99`，跨三份产物是
`780 ms`（合成 demo）/ `23836 ms`（`acme` 评测批）/ `59839 ms`（`__eval__` 含 LLM10 压力用例）——
**跨度约 76 倍，无一可代表生产**。把其中任一个当「本系统的 p99」对外陈述，都是错的。

**三档任选皆合规，选哪档都行，但必须选一档并写死：**

| 档 | 用法 | 对外口径 |
|---|---|---|
| **(a) 真实流量** | 最终权威 | 可引，**带下界标注**（n 不足时尤甚） |
| **(b) 代表性语料（assumed-mix）** | 可复算、今天能做 | 🔴 **比例当口径公开**；标签写死「assumed-mix vX · 攻击占比 Y% · 非生产实测」；**只在 NDA / 下界口径下给，不进对外 headline** |
| **(c) 标「未测定」** | 零成本、完全诚实 | 格子空着 / 明写「未测定 —— 无代表性流量」 |

**两条硬纪律：**

1. 🔴 **数字自带流量口径** —— 值和它的流量构成**同框出现**，不靠读者记得本文档
   （落点：measurement 的 `notes`，如 `block_rate` / `duration_p99` 已有的口径注）。
2. 🔴 **`block_rate` 在评测攻击流量上的排除是既有裁定，不得为「要个数」而翻。**
   评测批以攻击用例为主 ⇒ `block_rate` 在其上 DEGENERATE（≈全 block），是误导值；
   `treval/cli/collect.py` 的 `PASSIVE` 排除注释就是这条裁定的落点，不要绕过它硬凑一个数。

> **配对 delta 默认落 (b)**：它跑的是评测语料，正确表述是
> 「**在 <语料 sha> 这份攻击语料上，治理把得逞率从 X% 压到 Y%**」，
> **不是**「治理把生产得逞率压了 Z 个百分点」。**语料 sha + 构成必须与 delta 同框。**（见 EV-PAIR §0.1。）

> **合成值（如 demo 的 `duration_p99 780 ms`）永远不能替真实测量作证** —— 它已被 `synthetic_demo` +
> 渲染层「示例数据」三态标住；**任何工程结论（如「60s p99 blocker 已解决」）都不能建在它上面。**

## 7. 🔴 对外数字口径登记（跨仓 · PM 与架构师共签 · 2026-07-30）

**为什么单开一节**：以下四条此前散在各 issue、会议记录与对外材料里。
**散着的约定等于没有约定** —— 三个月后没人记得当初为什么这么定，然后有人"顺手"改一个。
**这里是它们的单一落点；改动须两侧同时改。**

| # | 约定 | 状态 |
|---|---|---|
| **1** | 🔴 **`injection_catch_rate` = 89%（n=28，95% CI [72.8%, 96.3%]）是唯一可对外引用的「机制侧」注入数。** 它纯读决策记录 ⇒ **不含模型自觉**。输出侧得逞率在 [EV-ATTRIB](issues/EV-ATTRIB.md) 落地前**一律撤或降级为口径下界** | ✅ 两侧已对齐 |
| **2** | 🔴 **`corpus_sha` 是对外材料版本的发布 gate**：**sha 没冻，不发带新 n 的版本。** 语料一次冻结 = 对外材料一次回填（n 与 sha 同一时点换；对外露 n，sha 在 NDA 报告里） | ✅ 共签 |
| **3** | 🔴 **覆盖率轴 ②（手法覆盖）对外只报清单 / 计数，永不报率** —— 没有外部分母，任何百分数都是假精确（[EV-COVERAGE](issues/EV-COVERAGE.md) §1.1）。生效时点 = 轴 ② 结果首次外发 | ✅ 共签 |
| **4** | **上游阈值（τ）= 保守下界 · 无剧退门 · 非 SLA**（PM 签框架，具体数字待共签）。Core 侧只登记该框架，**不引用其数值** | ⏳ 数字待定 |

**共同纪律（这四条为什么是一族）**：
**每个数都必须自带"它是在什么条件下、什么口径上成立的"** ——
`89%` 自带 n 与区间；新 n 自带 `corpus_sha`；手法覆盖自带"这是清单不是率"；τ 自带"这不是 SLA"。
**这就是 §6 硬纪律①在跨仓面上的同一条。**

> **口径只换一回**：一次评审、一次冻结、一个新 `corpus_sha`、对外材料回填一次。
> **不许某一页悄悄领先于实测。**
